## Domain 7: Automatic Storage Management (ASM) & Disk Groups

### ORA-15032: not all alterations performed
- **Description:** A composite ASM command (such as mounting disk groups or altering disk group properties) failed partially or completely.
- **Probable Causes:** Always accompanied by child errors (such as `ORA-15017`, `ORA-15063`, or `ORA-15038`) detailing the specific failure on one or more disk groups.
- **Resolution:**
  1. Inspect the subsequent error lines in the stack trace to find the root cause.
  2. Query `V$ASM_DISKGROUP` from the ASM instance (`+ASM`) to determine which disk groups remain unmounted.

### ORA-15040: diskgroup is incomplete
- **Description:** ASM cannot mount or access a disk group because one or more required disks or partner disks are offline or missing.
- **Probable Causes:** Fibre Channel/iSCSI path drops, OS disk permission changes (`/dev/oracleasm/*`), or storage array volume disconnection.
- **Resolution:**
  1. Inspect OS storage devices to verify disk visibility: `ls -l /dev/oracleasm/disks` or `multipath -ll`.
  2. Query `V$ASM_DISK` in the ASM instance to locate disks where `HEADER_STATUS` is `UNKNOWN` or `CANDIDATE`.
  3. If all physical paths are restored, mount the disk group: `ALTER DISKGROUP <dg_name> MOUNT;`.

### ORA-15063: ASM discovered an insufficient number of disks for diskgroup "string"
- **Description:** The ASM instance cannot discover enough valid member disks to assemble and mount the specified disk group.
- **Probable Causes:** `ASM_DISKSTRING` initialization parameter does not match the actual device paths, or storage ownership/permissions were reset after an OS reboot.
- **Resolution:**
  1. Check device permissions (should be owned by `grid:asmadmin` or `oracle:oinstall` with `0660`).
  2. Verify and broaden discovery paths in ASM:
     ```sql
     ALTER SYSTEM SET ASM_DISKSTRING = '/dev/oracleasm/disks/*', '/dev/mapper/*' SCOPE=BOTH;
     ```
  3. Attempt remounting: `ALTER DISKGROUP <dg_name> MOUNT;`.

### ORA-15077: could not determine instance location to connect to ASM
- **Description:** The RDBMS database instance cannot locate or establish communication with the local ASM instance.
- **Probable Causes:** ASM instance is down, Grid Infrastructure CSS daemon (`ocssd`) is not responding, or RDBMS executable lacks the setuid bit to communicate with the Grid home.
- **Resolution:**
  1. Check Grid Infrastructure clusterware status: `crsctl check crs` and `crsctl status resource -t`.
  2. Start the local ASM instance if down: `srvctl start asm -node <node_name>`.
  3. Verify permissions on the oracle executable: `$ORACLE_HOME/bin/oracle` should have `-rwsr-s--x` (mode 6751).

### ORA-15099: disk 'string' is too small; minimum size is string megabytes
- **Description:** An attempt was made to add a physical or logical disk to an ASM disk group that does not meet the minimum allocation unit and metadata footprint requirements.
- **Probable Causes:** LUN partitioned incorrectly or volume truncated.
- **Resolution:** Provide a disk partition that meets or exceeds the minimum size (typically > 100 MB, varying by allocation unit size).

## Domain 8: Real Application Clusters (RAC) & Cache Fusion

### ORA-29701: unable to connect to Cluster Synchronization Service (CSS)
- **Description:** The database instance cannot initialize or run in cluster mode because the CSS daemon (`ocssd.bin`) is inaccessible.
- **Probable Causes:** Grid Infrastructure stack is stopped, CSS daemon crashed, or network/IPC communication to the cluster stack timed out.
- **Resolution:**
  1. Check CSS status as the grid user: `crsctl check css`.
  2. Start cluster services if stopped: `crsctl start has` (standalone) or `crsctl start crs` (cluster).
  3. Review CSS log files in `$GRID_HOME/log/<node_name>/cssd/ocssd.log`.

### ORA-29740: evicted by member string, reason string
- **Description:** The local cluster node was evicted from the cluster membership by another node to preserve cluster-wide data integrity.
- **Probable Causes:** Private interconnect network latency/packet loss, split-brain condition, OS kernel hang/paging spike, or voting disk I/O heartbeats missed.
- **Resolution:**
  1. Review `$GRID_HOME/log/<node_name>/cssd/ocssd.log` and the OS system logs (`/var/log/messages`).
  2. Test private interconnect MTU and link health: verify Jumbo Frames ($9000$ MTU) match on all switches and interfaces.
  3. Inspect shared storage latency to the voting disks: `crsctl query css votedisk`.

### ORA-00439: feature not enabled: Real Application Clusters
- **Description:** An attempt was made to start an instance with `CLUSTER_DATABASE = TRUE` using an Oracle RDBMS binary compiled without RAC support.
- **Probable Causes:** The Oracle Home binaries were installed with RAC turned off, or were not linked against RAC libraries.
- **Resolution:**
  1. Relink the Oracle binary with RAC enabled:
     ```bash
     cd $ORACLE_HOME/rdbms/lib
     make -f ins_rdbms.mk rac_on
     make -f ins_rdbms.mk ioracle
     ```
  2. If running single-instance, reset `CLUSTER_DATABASE = FALSE` in your SPFILE/PFILE.

### ORA-00270: error creating archive log string (in RAC environment)
- **Description:** Archiver cannot write archivelog to a cluster-shared path or local staging directory.
- **Probable Causes:** Shared storage (NFS/ACFS/ASM) where archive logs are directed is unmounted or read-only on that specific cluster node.
- **Resolution:** Verify cluster filesystem mounts across all nodes, ensure ASM disk group has free space, and confirm archive destinations are identical across instances.

## Domain 9: Oracle Data Guard & Standby Database

### ORA-16014: log string sequence# string not archived, no available destinations
- **Description:** Redo log archiving failed because all configured mandatory archive log destinations (`LOG_ARCHIVE_DEST_n`) returned errors or were rejected.
- **Probable Causes:** Network disconnection between Primary and Standby, invalid service names, full destination disks, or bad authentication passwords.
- **Resolution:**
  1. Query `V$ARCHIVE_DEST` on the primary to identify destination error messages:
     ```sql
     SELECT dest_id, status, error FROM v$archive_dest WHERE status != 'INACTIVE';
     ```
  2. If the issue is remote standby connectivity, test TNS aliases: `tnsping <standby_tns>`.
  3. Temporarily defer failing optional destinations:
     ```sql
     ALTER SYSTEM SET LOG_ARCHIVE_DEST_STATE_2 = DEFER SCOPE=BOTH;
     ```

### ORA-16038: log string sequence# string cannot be archived
- **Description:** The primary database failed to archive an online redo log file, directly threatening an instance hang if all redo groups fill up.
- **Probable Causes:** Local disk full, permissions error on the directory, or accompanying `ORA-00257` / `ORA-16014`.
- **Resolution:** Clear space on the archive file destination disk or address the underlying I/O errors reported in the alert log.

### ORA-16191: Primary log shipping client not using same password file as standby
- **Description:** Log transfer service rejected connection because the password file (`orapw<ORACLE_SID>`) on the Primary and Standby do not match.
- **Probable Causes:** SYS password was changed on the Primary without recopying the password file to the Standby, or the format (`orapw`) does not match.
- **Resolution:**
  1. Copy the primary password file to the standby server:
     ```bash
     scp $ORACLE_HOME/dbs/orapw<PRIMARY_SID> standby_host:$ORACLE_HOME/dbs/orapw<STANDBY_SID>
     ```
  2. Ensure permissions on the destination password file match the oracle user.
  3. Restart redo transport on the Primary:
     ```sql
     ALTER SYSTEM SET LOG_ARCHIVE_DEST_STATE_2 = DEFER;
     ALTER SYSTEM SET LOG_ARCHIVE_DEST_STATE_2 = ENABLE;
     ```

### ORA-16000: database or pluggable database open for read-only access
- **Description:** A DML statement (`INSERT`, `UPDATE`, `DELETE`) or non-temporary DDL was attempted on an Active Data Guard (ADG) physical standby opened in `READ ONLY` mode.
- **Probable Causes:** Directing write operations or application update traffic to a standby database intended strictly for reporting.
- **Resolution:**
  1. Route write transactions to the Primary database.
  2. If using DML redirection (Oracle 19c+), verify `ADG_REDIRECT_DML = TRUE` is enabled on the session: `ALTER SESSION ENABLE ADG_REDIRECT_DML;`.

### ORA-16086: standby database does not contain available standby redo log files
- **Description:** Redo transmission in real-time apply or zero-data-loss mode failed because no suitable standby redo log (SRL) was available.
- **Probable Causes:** SRLs were not created on the standby, or their size does not match the online redo logs (ORLs) of the primary.
- **Resolution:**
