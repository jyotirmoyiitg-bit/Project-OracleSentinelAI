1. Where it stands

One portal and one API process monitor registered Oracle databases through a single read-only account, with no agent on the database hosts.

CapabilityWhat an operator getsSince
MonitoringScheduled metrics, alert-log reading, incidents, compliance results, growth forecast, portal and email notificationsPhases 2 to 4

CopilotA database chat and a fleet chat. A supervisor sends each question to the right specialist; answers show their rows and cite manual pagesPhases 6, 9, 18, 20, 21, 24

3. How the architecture evolved

Three snapshots of the same system. Highlighted rows are what that stage added. Nothing was removed along the way; every later part sits on the first five rows.

Why it changed the way it did

ChangeWhat drove itWhat it cost
One process, not a worker fleetThe plan allowed Celery and Redis later. Keeping the scheduler inside the API meant one thing to start and one log to read while the product was still being shaped.No second node. Two switches need a restart. A slow poll shares the process with the portal's requests.
A readings server instead of a SQL toolThe copilot needed live facts, but a model must never write SQL. A child process that accepts only a reading name and a TNS alias removes that path entirely, and needs no listening port.A process start and an Oracle logon for each reading, a second or two each.
Vectors in PostgreSQLOne database to back up and secure. pgvector was enough for tens of thousands of passages.The vector length is fixed in the schema, so changing the embedding model family needs a migration (Phase 24 did one).
Settings moved from .env to the databaseAn administrator should change a threshold in the portal, with an audit row, and not edit a file on the server.A stored value silently wins over .env, which surprises anyone who edits the file afterwards.
Live views built one panel a phaseGraphDB took six phases (11 to 16). Each added one panel and one launcher, so a fault could only be in the newest panel.Many small phases and many launchers to maintain.
The model moved from narrator to router to investigatorPhase 6 let it only explain rows. Phase 20 let it nominate readings from a list. Phase 22 let it plan and conclude inside a playbook. Phase 24 made it the supervisor. Each step was taken only after the previous one proved safe, and each kept a check in plain code behind the model.More model calls per question (about 0.8 seconds for the supervisor), and behaviour that must be measured, not assumed.
Storing more, in small stepsEarly phases stored only scheduled metrics. Agent snapshots (14 days) and counter samples (24 hours) were added when a feature needed a "before" to compare with.Three kinds of history with three retention rules to explain.

4. Decisions and reasons

The project is defined as much by what it refuses to do as by its features.

Rules that held through every phase

RuleSet inReasonHow it is enforced
No SQL from an operator or a modelPhase 0, 6A monitoring tool that can be talked into running a statement is a risk on a production database.Every statement is a fixed entry in a catalog. A pasted statement is refused. The readings server has no SQL argument.
Read-only account, nothing created in OraclePhase 1The tool must be safe to point at any database.GSYSTEM has CREATE SESSION and SELECT on listed views. Tests compare the grants with the statements.
No agent on the database hostPhase 0, 3Nothing to install, patch, or justify on a Windows database server.Even the alert log is read over SQL.
No AWR, ASH, or ADDMPhase 0They need the Diagnostics Pack licence.Rates and forecasts are computed from the application's own samples.
Monitoring works with the model offPhase 0A model outage must not blind the operator.Collection, incidents, and the live views never call a model. The copilot falls back to the rows.
Execution stays offPhase 7, 8Changing a database needs a security review that has not happened.Proposals are stored only. The privileged routes answer 501. The switch cannot be saved in the portal.
A company requirement comes only from a policy documentPhase 9, fixed in 24Oracle guidance is not company policy.A policy question searches policy documents only.

Rules that were relaxed, deliberately

Earlier ruleChanged inNew ruleWhy, and the guard that stayed
The model never chooses a readingPhase 20, 24The model names readings from an allowlist; since Phase 24 a supervisor picks the specialistKeyword routing got 35 of 53 test questions right, the supervisor 51. The server checks every name, and two fixed rules sit behind the model.
Fleet chat does not read a databasePhase 21Two fleet questions read every enabled database live"Which database runs this program" could not be answered from stored data. Capped at 25 databases, four at a time, 45 seconds each.
GraphDB is for administratorsPhase 17Every role, with file listings for administratorsOperators are the audience. Paths and names stay restricted.
Rates are never storedPhase 23Counter samples are stored for 24 hoursPages opened empty. Samples never enter the health or rule tables.
Passage vectors are a local word hashPhase 24A local embedding modelWord hashing matched words, not meaning. The model must run on the same computer; the address is fixed.

Course corrections

MomentWhat was proposed or assumedWhat was done instead, and why
Phase 22An agent that polls database information into PostgreSQLA plain Collector with no model stores fixed readings; the model reasons only over what was stored. Polling needs to be predictable, not clever.
Phase 23That agent data would fill the graphs before live data arrivedIt could not: agents are off by default and run on request. The always-on scheduler stores the counters, and the page takes a second reading after 3 seconds.
Phase 24That the manuals were searchableThey had never been indexed here, and the page limit would have rejected most of them. Limits were raised and indexing became a tracked one-time step.
Phase 24That a policy answer rested on policyA real-model run showed a manual passage reported as company policy. Policy questions now search policy documents only.
Phase 25That synthetic tests proved the new statementsThe real database rejected one statement and exposed a wrong severity rule. Both were fixed before the phase closed.

6. Strengths and weaknesses of the Quarter 1 state

An honest reading of what was built, for deciding what to do next.

Strengths

  • Safe by construction. There is no code path from a prompt to a statement. The account is read-only, the catalog is fixed, and nothing is installed on the database host. This is a claim most AI database tools cannot make.
  • Useful with the model off. Monitoring, incidents, and all six live views need no model. The copilot degrades to the rows.
  • Local first. The language model and the embedding model run on the same computer, so database facts and document text stay inside.
  • Evidence is visible. Every answer lists its reading and its citations, and an agent's cause is shown only when plain code finds every figure in the evidence.
  • Simple to run. Two processes and PostgreSQL. No message broker, no separate vector store.
  • Operable from the portal. 138 settings, most editable in Admin with an audit row, and a document that lists every switch.
  • Well tested for its age. 619 tests, real-model evaluations for routing and investigations, and a live launcher for 23 phases.
  • No licensed packs. Everything works on Standard Edition views.

Weaknesses

  • Proof on real databases is thin. Most full launchers were written and not run in the sessions that wrote them. Phases 22 to 25 have not been run end to end against Oracle.
  • Four phases are uncommitted. 72 changed files and 42 new entries sit on top of the Phase 21 commit. One mistake could lose them.
  • One process, one node. The scheduler, the timers, and the portal's requests share a process. There is no failover, and scale beyond a few dozen databases is untested.
  • Little shows by default. The scheduler, agents, model, and knowledge scan are all off on a fresh installation, so the first impression undersells the product.
  • History is shallow. Counter samples last 24 hours and the charts have no time axis. There is no "compared with last week".
  • The copilot's quality is measured on our own questions. The 53 routing questions were written here, not collected from operators. Manual citations often read "Page N".
  • It advises and never acts. By design, but it means a finding ends as text. The loop from finding to approved change is not built.
  • Maintenance weight. Twenty-three launchers, a 1,096-line App.tsx, one 1,216-line stylesheet, and lint findings in 13 older files.
  • Oracle only, Windows launchers only. The adapter contract for other engines exists but is empty.

7. What would make it stand out

Ordered by value for the effort. The first two are about trust; the rest build on data the product already collects.

Close the proof gap Do first

Commit Phases 22 to 25. Run every launcher on a real database once. Add one regression launcher that runs them all, and a CI run for the tests.

Why: every claim in this page then rests on a recorded run, and the work cannot be lost.

A first-run setup page Do first

One page that shows each switch from architecture v3 with its current state and a button, and checks Ollama, the grants, and the index.

Why: the product is off by default, and a new user should reach a working monitor in five minutes.

Daily fleet brief High value

Each morning, one page: what changed overnight on every database, what is growing, what failed, what needs a decision. Built from the snapshots, history, and incidents already stored.

Why: it is the thing a DBA team would open every day, and no reading or grant is missing for it.

Drift detection High value

Store ParameterDB, users, and file lists once a day and compare with yesterday and with a baseline. Show "three parameters changed on FINANCE since Tuesday", and which databases differ from their peers.

Why: unexplained change is the first question in most incidents, and few tools answer it without licensed packs.

From finding to draft proposal High value

An Advisor that turns an accepted finding into a draft proposal with its pre-checks, for a human to approve. Execution stays off.

Why: it closes the loop from "what is wrong" to "what we will do", using the proposal flow built in Phase 7.

Trends and "is this unusual" High value

Keep counter samples longer in a thinned form, draw them on a time axis, and mark a value that is far from the same hour last week.

Why: a rate means little without knowing what is normal for that database.

Learn from operators High value

A thumbs up or down on every answer, stored with the question and the route. Use them as the evaluation set for the supervisor and the search.

Why: quality is currently measured on questions written here. Real ones would show the real faults.

Better manual answers

Split the manuals by their real headings, add a reranking step, and show the page as a link.

Why: a citation that reads "Page 2338" is hard to trust. A heading and a link are not.

Alerts where the team already is

Teams, Slack, or a webhook, with maintenance windows and a quiet period per database.

Why: email alone is easy to miss, and there is no way today to silence a planned outage.

A worker process and a second node Later

Move the timers to a worker, as the original plan allowed, and share the sign-in throttle.

Why: needed for a large fleet or for failover, and not before.

A second engine Later

Fill the SQL Server or PostgreSQL adapter behind the contract that already exists.

Why: the safety model is the product; it is not specific to Oracle.

Guarded execution Later

After a security review: a small set of fixed changes, with pre-checks, dual approval, and a recorded result.

Why: it is the largest step in value and in risk, so it comes last and only with review.
