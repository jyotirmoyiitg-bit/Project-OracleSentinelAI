Oracle Sentinel AI · Phase 22 · design proposal

Agents that collect evidence, investigate incidents, and brief the operator

Today the copilot answers one question at a time and keeps nothing. Phase 22 adds agents that work toward a goal over several steps, store what they read from Oracle in PostgreSQL, and hand the operator a finding with its evidence.

Status Phase 22 built (Collector, Investigator, Verifier, settings); Fleet analyst and Advisor not built Builds on Phase 20 routing and audit, Phase 21 fleet tools Model local, qwen2.5-coder:14b Access to Oracle read-only, unchanged

Recommendation

Your idea is the right foundation, with one change. Fetching rows from Oracle does not need a language model, so the poll should be a plain collection tool that agents call. It runs the existing fixed readings and stores the rows in PostgreSQL as a snapshot. The agents then reason over stored snapshots.

Build one supervisor and four narrow agents: a Collector (your idea), an Investigator for incidents, a Fleet analyst for the daily picture, and an Advisor that drafts a proposal for a person to approve. A Verifier checks every finding against its evidence before the operator sees it. No agent writes SQL and no agent changes a database.

What stored snapshots change

The scheduled collectors already store six probes: connectivity, instance, storage, recovery area, resource limits, and configuration. The 28 copilot readings (sessions, blocking, top SQL, memory, redo, jobs, backups, alert log and the rest) run live and their rows are thrown away after the answer. That is the gap your idea closes.

What the operator gains

  • "What changed on this database since yesterday" becomes a stored comparison.
  • A fleet question can be answered from the latest snapshot with its age shown. Today each program or datafile question logs on to every database.
  • Evidence from before an incident is still there when the database is down or the session has gone.
  • Sessions, memory, and redo activity get a history, which the app does not have now.
  • Every sentence in a finding can point at a stored row.

What it costs, and the control for each

  • Storage grows. Keep snapshots for 14 days by default, then delete them. Runs and findings stay, with the figures they cite.
  • Each collection is load on Oracle. Allow one collection per database at a time, with a minimum gap between them.
  • Snapshots hold session user names and SQL text. Store those only in the admin-only pack and filter by role on every read.

Guardrails

Rules that stay as they are

  • No operator text and no model text is ever placed in a SQL statement.
  • Only the fixed, read-only readings reach Oracle, through the GSYSTEM account.
  • The model is given no tool to call. It names a step; the server checks the name against the allowlist and the operator's role, then runs it.
  • Privileged execution stays disabled. A proposal waits for a person.
  • AWR, ASH, and ADDM are not queried.

Rules added for agents

  • A budget on every run: 6 tool steps, 4 model calls, 3 minutes, one run per database at a time.
  • A run acts with the role of the person or rule that started it. Admin-only packs stay admin-only.
  • Alert log text and SQL text in a snapshot are data. They are sanitized and never read as instructions.
  • A finding that fails the Verifier is never shown as a conclusion.
  • One switch, AGENTS_ENABLED, turns every agent off. It ships off.
  • Fleet rows go only to the local model, as in Phase 21.

Settings

Each behaviour is a parameter with a system default. A database can override it. The database value wins; a database with no value of its own uses the system default. Only an administrator changes either, and each change is audited.

These five tables need Alembic revision 0011. This is a build step, not a setting: without it there is nowhere to store snapshots or database overrides. The Phase 17, 20, and 21 launchers check for head 0010 exactly, so they are changed to accept a later head in the same phase.

Where it appears in the portal

  • Incident page. An Investigate button, the run timeline as it happens, and the finding with Accept and Dismiss. Draft a proposal arrives with the Advisor in a later phase.
  • Database Overview. Collect snapshot, the time of the last snapshot, What changed since the previous one, and Investigate for the database.
  • Copilot (database chat built in Phase 24; fleet later). Fleet answers can come from the latest snapshot with its age shown and a Refresh that reads live. "Investigate this" hands the question to the Investigator.
  • Agents page in the top bar. Recent runs and open findings.
  • Admin, new Agents section, for the system defaults. Database settings for that database's overrides, each showing whether it is its own value or the system default.
  • Fleet page (later phase). The daily brief: what changed, what is growing, what needs attention.

Delivery

  1. Phase 22A: snapshot store and Collector. Revision 0011, snapshot packs, Collect snapshot, What changed, retention, permission agent.run, audit rows. Useful on its own and needs no model.
  2. Phase 22B: Supervisor, Investigator, Verifier. Playbooks for the common incident types, the run timeline, findings on incidents, and the on-incident trigger behind a setting.
  3. Later phase: Fleet analyst and Advisor. Drift and growth across the fleet using the existing forecasting module, the daily brief, proposal drafts from accepted findings, and copilot answers from stored snapshots.

Left out on purpose

  • Agents that talk to each other freely. A 14b local model is reliable on one small JSON decision, not on long open conversations.
  • A model call inside the poll. It adds delay and risk and no value.
  • An agent framework dependency. The run loop is small, and writing it in the project keeps every step in the audit trail.
  • Agents that execute changes.

Decided

  • Snapshots are kept for 14 days by default and then deleted.
  • Retention, automatic investigation, and collecting SQL text and user names are settings, with a system default and a database override.
  • Revision 0011 is added, because snapshots and database overrides need tables.

Still to confirm

  • Stored SQL text and session user names stay readable by administrators only, with no setting to open them to other roles.
