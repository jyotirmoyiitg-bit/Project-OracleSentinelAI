Oracle Sentinel AI

High-level architecture, request flow, and the processes that implement it. Open this file in a browser. The readings server is not a port and does not stay running.

Portal :5173 API :8000, always on Readings process, one question Oracle, read-only GSYSTEM PostgreSQL Local model, optional

1. High-level architecture

Operators use the portal. The API on port 8000 is the long-running application. A database question starts a separate readings process, which exits after one answer.

2. Data flow

Collection does not need a language model. A copilot question on a selected database takes the second path and always returns the rows, even when Ollama is off.

Always on
Scheduled collection. The API scheduler polls each registered alias on its interval.
  • Health, tablespace, FRA, alert log, and configuration probes run as GSYSTEM.
  • Rows are stored in PostgreSQL. Rules open incidents. Forecasts use retained samples.
  • Approved files in the knowledge folders are parsed and embedded locally. Collection never reads those files to decide what SQL to run.
On ask
One database question. Fleet chat does not open Oracle. The question must be asked on a database.

3. Implementation

Two Python processes share one code tree. The API process owns the decision. The child process owns the Oracle call for that question.

Boundaries that stay in force

Monitoring stands alone

Collection, rules, and incidents keep running when Ollama is stopped and when no question is being asked.

Read-only Oracle

GSYSTEM has SELECT on listed views. The catalog is the only SQL. AWR, ASH, and ADDM are not used.

Evidence stays visible

The answer lists the reading under the narration. Tool calls are stored. A wrong or vague model sentence does not replace the rows.
