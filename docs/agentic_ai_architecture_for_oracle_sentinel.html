Oracle Sentinel AI — Agentic Architecture

The agents, the copilot, and the snapshot store · as built through Phase 28 · 20 Nov 2026

This page covers only the agentic part of the portal: which agents exist, the goal of each, how they reach Oracle and the local model, what a snapshot stores, and how the agents serve the operator, the administrator, and the database copilot. It ends with the changes that would make the agents more useful in the web portal, and with agents worth adding.

1In short

Two agents, one checker

The Collector stores snapshots. The Investigator works out the likely cause of an incident. The Verifier is plain code that rejects any conclusion the evidence does not support. Every run is stored in agent_runs as either collector or investigator.

Agents read; they never change anything

Agents reach Oracle only through the fixed read-only readings, as GSYSTEM. The model gets no tools and writes no SQL, and nothing it writes goes into a statement.

Evidence stays local

Only the local Ollama model sees evidence. With a hosted provider, or with the model off, a finding lists the evidence and the playbook's next steps, without a written cause.

Off by default, mostly on demand

Agents ship turned off (Admin → Agents). Snapshots are taken only when someone clicks, or when an investigation needs one. Nothing collects snapshots on a timer, so "what changed" and copilot answers from snapshots often have nothing recent to use. See section 9.

2The agents and their goals

"Agent" here means a component that works toward a goal over several steps and keeps what it read. The copilot parts are listed too, because they use the same readings and the same snapshots. The monitoring timers are not agents, but they produce the incidents and metrics the agents reason over.

Agents (Phase 22)

Collector no model

Goal: store a consistent picture of one database at one moment.

Reads the readings of the chosen packs over one readings-server process and one Oracle logon, then stores one evidence_snapshots row per reading. A collection is refused when agents are off, when the database is disabled, when a collection is already running, or when the last one is newer than the minimum gap (300 s).

Investigator local model

Goal: explain the likely cause of one incident, or one database's health, with numbered evidence and up to three next steps.

Follows a fixed playbook: plan → collect → compare → look up → conclude → (collect more) → verify → finding. Limits: 6 tool steps, 4 model calls, and 180 s per run, with one run per database at a time.

Verifier plain code

Goal: make sure no operator sees a cause the evidence does not support.

A conclusion passes only when every ORA code and every figure of two or more digits is in the evidence, when it names no other database, and when it contains no statement or command. A conclusion that fails is hidden, and the finding gives the reason.

Agent scheduler timer

Goal: investigate new critical incidents without waiting for a person, and remove old snapshots.

Every 60 s it starts up to 2 investigations for critical incidents from the last 24 h that have none yet, when the database allows automatic runs. These runs act as an operator, so every role can see their findings. Every hour it deletes snapshots older than the retention period (14 days).

Copilot (Phases 21, 24, 26)

Supervisor local model

Goal: send each database-chat question to the right specialist.

One model call returns JSON with at most 2 routes and 3 reading names. The server keeps only the routes it lists and the readings the caller may read. Fixed rules sit in front of the model (a pasted statement is refused, catalog questions skip it) and behind it (an explicit change phrase is always a change request).

Specialists local model

Goal: answer from one kind of evidence only.

The six specialists:

  • This database: live readings, or a snapshot up to 15 minutes old.
  • Oracle knowledge: the Oracle manuals, embedded locally.
  • SQL draft: writes a statement that is never run.
  • Company policy: policy documents only.
  • Change request: an explanation or a runbook; nothing is run.
  • General: a short reply with no database facts.

Fleet copilot local model

Goal: answer one question about every database.

A fixed router picks a fleet tool: incidents, programs, datafiles, tablespaces, policy, or health. The model may name a tool only when the router finds none. Live reads cover at most 25 databases, 4 at a time. A database that cannot be read is reported as unknown, never as clean.

Why a snapshot is worth keeping, beyond the live pages

  • Evidence after the fact. Locks, sessions, running jobs, and top SQL disappear within minutes. A snapshot keeps them for the investigation and for a person reviewing it the next morning.
  • "What changed" without AWR. Two snapshots compared in plain code give new errors, new sessions, and moved values. This works on Standard Edition, without the Diagnostics Pack.
  • Grounding for the model. Every figure and ORA code in a cause has to come from these rows, so they are what the Verifier checks against.
  • Less load on Oracle. A recent snapshot answers the copilot and the Investigator without another logon.
  • Findings that stay explainable. Snapshots are deleted after 14 days, but each finding keeps the figures it cites.

Three scenarios

Archiver stuck at 02:10

The alert-log poll raises a critical incident for ORA-00257. Within 60 s the sweep starts an investigation, and the rule matches the archive-destination playbook. The run collects recovery, backups, redo logs, and errors, and compares the recovery area with its value a day ago. The local model cites evidence lines 2 and 4, and the Verifier passes it. In the morning the on-call operator opens one finding with a cause and three checks, and accepts it.

A DBA before and after a release

The DBA clicks Collect snapshot on the Overview, the release runs, and they click it again. What changed lists new ORA errors, a tablespace that grew 6 points, and the program that now holds 40 more sessions. No model is involved, and nothing is written to Oracle.

A copilot question

An operator asks the database copilot "How full is the USERS tablespace?". The supervisor routes it to This database. The snapshot from 4 minutes ago answers, and the reply says it came from the snapshot. Asking "…right now?" reads Oracle live instead.

8Using the agents in the portal today

  1. Turn agents on. As an administrator, open Admin → Agents and switch AGENTS_ENABLED on. Until then every start button is hidden, and the API answers 409 AGENTS_OFF.
  2. Choose per database. On each database's Overview, open Agent settings for this database. Keep automatic investigation off at first, check the packs (core and performance), and turn off sensitive readings for databases with regulated data.
  3. Take a first snapshot. Click Collect snapshot on the Overview, or Collect fleet snapshot on the Agents page. A second snapshot later fills What changed.
  4. Investigate. Use Investigate on an incident page (best, because the incident text picks the playbook) or on the Overview (General health check unless a rule matches).
  5. Review. Open the Agents page for open findings across the fleet. Accept or Dismiss each one; the decision is audited.
  6. Then automate. Turn on AGENT_AUTO_INVESTIGATE for the databases where an unattended first diagnosis is welcome.

10Agents worth adding

Each proposal reuses the snapshot store, the fixed readings, the local model, and the Verifier, so none of them needs a new way into Oracle. Two of them (Fleet analyst, Advisor) were planned in Phase 22 and never built.

Proposed agents

Drift watcher no model priority 1

Goal: raise a finding when a scheduled snapshot differs in a way that matters.

Runs after each scheduled snapshot, using the existing compare code. It reports new ORA codes, a newly failed job, a tablespace up 5 points in a day, a program whose sessions doubled, and a restart. It turns What changed from a panel someone has to open into an alert.

Capacity forecaster no model priority 2

Goal: warn days before a tablespace or the recovery area fills.

Uses the growth reading, used_pct_of_max from Phase 27, and the existing sentinel/forecasting code. It writes a finding such as "USERS reaches its maximum in about 9 days at the rate of the last 7", with the samples it used.

SQL regression analyst local model priority 3

Goal: spot a statement whose plan changed and got slower.

Compares SQL workload snapshots by SQL_ID and plan hash value, which Phase 28 already reads, and by elapsed time per execution. It answers the copilot catalog question "SQL regressions", which today says the data is not collected. Its findings are admin only, because they contain SQL text.

Backup and recovery auditor no model priority 3

Goal: check every morning that each database meets its backup policy.

Compares the backups and recovery readings with the policy documents' rules (for example, a full backup within 7 days and archived logs within 24 h). The result is stored as a compliance result plus a finding, so it shows in the existing policy views.

Security drift auditor no model admin only

Goal: report security changes between two configuration snapshots.

New privileged role grants, accounts unlocked, new schemas, and new invalid objects. It runs only on databases where an administrator has turned on the configuration pack.

Fleet analyst local model planned in Phase 22

Goal: a daily brief, one page for the whole fleet.

It reads findings, incidents, and health from the stores, with no Oracle reads. The model writes the summary and the Verifier checks every figure in it. Shown on the Agents page and optionally sent by email through the existing notifier.

Advisor local model planned in Phase 22

Goal: turn an accepted finding into a reviewed change proposal.

It drafts the runbook steps and a proposal for the existing privileged-operations approval queue. It never runs anything: privileged execution stays disabled, and a person still does the work.

Suggested order: scheduled collection → Drift watcher → AgentDB tab → Capacity forecaster. The first two need no model and no new grant, and they make every existing agent more useful. The SQL regression analyst and the Advisor need the most care, because they handle SQL text and change proposals.

11Guardrails that stay in place

Oracle

  • Only fixed SELECT readings, as GSYSTEM. Nothing writes to Oracle.
  • Only whole numbers and SQL_IDs in Oracle's own format may be bound (Phase 28). Text from a person or the model is never bound.
  • No AWR, ASH, or ADDM, so no Diagnostics Pack licence is needed.
  • One logon per snapshot, a minimum gap, one collection at a time, and one investigation per database.

Model

  • Evidence goes only to the local model. A hosted provider gives findings with evidence only.
  • The model has no tools. It may choose names from fixed lists (playbooks, readings, routes) and nothing more.
  • The Verifier stands in front of every written cause.
  • A company requirement is stated only from a policy document.

People and data

  • User names, SQL text, object names, paths, and configuration are for administrators only.
  • A run acts with the role of whoever started it. Automatic runs act as an operator.
  • Snapshot collection, runs, decisions, and settings changes are written to the audit log.
  • Snapshots are deleted after 14 days. Findings keep the figures they cite.

12Should the Investigator run a bounded loop with tool calling?

Today the Investigator follows a fixed path, and the model only fills in JSON. This section looks at whether a short loop, in which the model calls read-only tools for 3–5 turns, would suit a monitoring portal like this one. It covers what that would add, the costs, and what to do.

What the current deployment has

There is a harness but no loop. AgentRunner (agents/runner.py) wraps each run and controls what it may do, but the order of the steps is fixed in code:

Budget6 tool steps and 4 model calls, checked before each step

What it would bring

  • It follows the chain. From blocking, to the head SID, to its statement, to the cached plan in one run. Today that takes three pages: WaitDB, SessionDB, and the plan tab.
  • Fewer General findings. When no playbook matches, the model looks further instead of reading six fixed readings and guessing.
  • It checks history. "Was this already high yesterday?" and "Has this database had this finding before?" are answered before it blames a recent change.
  • Less unneeded reading. It reads what the evidence points to, rather than every reading on a playbook's list.

Pros and cons

Pros

  • The tools already exist as read-only MCP tools on an allowlist
  • The harness parts already exist: budget, deadline, step log, role filter, and Verifier
  • Causes that cross areas, which a fixed playbook misses
  • Stored-data tools add history without extra load on Oracle
  • Safe by construction: no SQL from the model, no writes, and today's path as the floor
  • Each turn and call is visible in the portal and the audit log

Cons

  • Slower. About 3–8 s per model call on qwen2.5-coder:14b, so 20–40 s per investigation. Fine in the background, slow in a chat.
  • Tool-call reliability of a local 14B model. Ollama supports tool calls for qwen2.5, but it needs testing here. Keep the JSON fallback.
  • Less predictable. Two runs of the same incident may read different things, which makes runs harder to compare.
  • More Oracle reads per run. Bounded by the call limits and snapshot reuse.
  • More text from Oracle reaches the model (alert log lines, SQL text). The tools cannot write, but this text has to be treated as untrusted.
  • More to build and test. New stored-data tools, a tool-call parser, and an evaluation set.

Recommendation

Yes, for the Investigator only, with up to 4 model turns. Build it as one small phase behind AGENT_LOOP_ENABLED:
  1. Scheduled snapshot collection first (§9). Without fresh snapshots, what_changed and get_metric_history have little to give the loop.
  2. Add the stored-data tools, get_past_findings, and finish. Turn the single "collect more" round into the bounded loop, keeping today's path as the first pass and the fallback.
  3. Decide on evidence. Replay about 20 past or synthetic incidents through both paths, and compare the Verifier pass rate, evidence cited, General findings, and time taken. Keep the loop only if it wins.
  4. Only then consider the same loop for the database copilot's "why" questions.
