Architecture Whitepaper · Concept / HLD · 08 November 2026

Oracle Sentinel AI

An agentic, RAG-enabled monitoring and diagnostic assistant for Oracle Database on Windows Server — combining proactive anomaly detection, reactive incident triage, traceable recommendations, alert notifications, and a conversational DBA copilot.

Windows ServerOracle DatabaseRead-only SQL monitoringWindows Event LogsOracle ADR / alert logAgentic orchestrationPDF / DOCX RAGHuman-in-the-loop
Audience: Solution architects, Oracle DBAs, Windows administrators, SRE / operations, security and engineering leads. Status: Proposed design, not a deployed product.

01. Executive summary

The solution continuously observes Oracle database and Windows host signals; detects rule-based failures and emerging trends; invokes allowlisted, read-only diagnostic tools; retrieves relevant Oracle documentation and internal procedures through RAG; and creates structured alerts with evidence, likely causes, recommended actions, and references. DBAs can also ask natural-language questions through a secure web chat.

Observe

Collect reliable signals

Oracle views and ADR events, Windows event channels, host performance counters, service health, filesystem capacity and backup status.

Reason

Correlate and investigate

Deterministic detection starts the workflow; specialist agents collect evidence, query the knowledge base and propose ranked hypotheses.

Act safely

Notify and assist

Send deduplicated alerts, produce cited triage summaries and suggested runbooks. Changes remain under DBA change-control.

Recommended starting principle: Make the monitoring and alerting path deterministic and independently operational. Use AI to enhance correlation, explanation, triage and chat — not as the sole mechanism deciding whether a critical outage should be reported.

What “proactive” realistically means

The first release should forecast trends and surface warning signs (for example, rapidly increasing FRA occupancy or declining free space), not promise perfect failure prediction. Its recommendations must carry measurable evidence, confidence, uncertainty, and explicit next checks.

03. Target logical architecture

A central AI control plane can run in a segregated Windows or Linux VM/container environment, while small collectors run on or near each monitored Windows host. Only approved outbound telemetry and read-only DB connections are required.

Figure A — end-to-end solution components and trust boundaries
Solid arrows: typical event or request path. Dashed arrows: storage, policy or secondary interactions. The orchestrator is not allowed to directly run arbitrary SQL, PowerShell or OS commands.
Deployment choice: Prefer central AI services and a small host-side collector or Windows Event Forwarding infrastructure. Read-only SQL sampling may run centrally through a narrowly allowed database listener route. Keep log and metric collection functioning during LLM/provider outages.

04. Data-flow diagrams

Flow 1 — proactive monitoring and early warning

Telemetry → trend assessment → recommended prevention
1. Scheduler triggers safe SQL + host sampling
→
2. Store timestamped baselines and changes
→
3. Rule/trend engine finds growing risk
→
4. Agent gathers extra evidence + RAG guidance
→
5. Notify DBA with preventive steps

Example: FRA usage grows from 74% to 89% over six hours. A policy threshold plus trend suggests probable exhaustion. The agent checks reclaimable space, recent ORA errors, archiving-related signals and the approved recovery-area runbook before warning the DBA. This is risk detection, not guaranteed prediction.

Flow 2 — reactive incident and triage

Detected failure → triage → incident lifecycle
1. Oracle ORA error / Windows event / unreachable target
→
2. Rule instantly opens or updates incident
→
3. Notify critical on-call path immediately
→
4. Agent gathers diagnostics + cites runbook
→
5. Enrich ticket; DBA acknowledges / resolves

Reliability rule: A severe deterministic condition must trigger a minimum viable notification before AI analysis finishes. AI enriches the incident asynchronously; it never blocks the initial alert.

Flow 3 — conversational DBA copilot

Authenticated request → authorized tools → grounded reply
1. DBA asks: “Why is DB01 slow?”
→
2. AuthZ checks target and tool scope
→
3. Agent plans approved read-only tool calls
→
4. Retrieve timestamped metrics + RAG
→
5. Answer with evidence, citations, caveats

Anti-pattern: Sending arbitrary LLM-generated SQL directly to a production database. Chat queries should resolve to versioned, parameterized and cost-bounded diagnostic templates.

Flow 4 — knowledge-base indexing

Approved documents → controlled retrieval index
1. Approved PDF, DOCX, SOP, vendor notes
→
2. Parse, OCR if needed, remove secrets
→
3. Section-aware chunk + metadata
→
4. Embed + keyword index + version
→
5. Retrieve, rerank, cite, expire outdated docs

Offline ingestion is separate from online diagnosis. The LLM receives only authorized, relevant document excerpts and always distinguishes vendor guidance from internal organization-specific procedures.

Never expose an unrestricted execute_sql(sql) or run_powershell(command) agent tool against production. Even queries that begin with SELECT can be expensive or invoke functions with side effects. Use template allowlists, least-privilege identities, resource limits, timeouts, audit and row limits. A database READ ONLY transaction or a text-based SQL filter by itself is not a sufficient control.

07. RAG knowledge architecture

RAG is used to ground the agents in documentation and validated operational knowledge — not as a substitute for querying real-time instance health. Health information comes from tools; procedural guidance comes from indexed knowledge.

Ingestion / offline

Approved knowledge corpus

  • Oracle manuals and vendor PDFs (where legally permitted)
  • Internal Word SOPs, architecture diagrams and runbooks
  • Historical incident writeups and approved postmortems
  • Organization-specific escalation and maintenance policies

Parse sections/tables; clean headers; extract version, product, DB release, document owner, effective date, access label, source URI and page/heading; then chunk, embed and index.

Retrieval / online

Answer grounding

  • Route ORA-code questions to exact-keyword + semantic retrieval
  • Filter by Oracle release, OS, environment and document ACL
  • Retrieve top candidates and optionally rerank
  • Attach page/section citations and confidence qualifiers
  • Reject stale or conflicting instructions, or surface conflict

Use hybrid BM25 + vector search as a strong starting point; prefer exact matching for error codes and commands.

Knowledge metadata example

{
  "doc_id": "RUNBOOK-FRA-004", "title": "Fast Recovery Area Response",
  "document_type": "internal_runbook", "product": "Oracle Database",
  "version_scope": ["19c"], "os_scope": ["Windows Server"],
  "section": "Preventive checks", "page": 7,
  "effective_date": "2026-08-01", "review_status": "approved",
  "access_group": "DBA_OPERATIONS", "source_uri": "internal://runbooks/fra",
  "content_hash": "...", "chunk_id": "RUNBOOK-FRA-004:7:2"
}

Failure controls for RAG

Track retrieval Recall@k, citation correctness, groundedness, missing-source rate and outdated-document hits. Build a golden set of known ORA-code scenarios, including conflicting Windows vs Oracle symptoms. Prevent document text from overriding system policies: retrieved files are untrusted data, even if they look like instructions.

08. Two operational scenarios

Proactive

Risk of FRA exhaustion

Trigger: >85% current FRA utilization and sustained positive growth in a defined window (illustrative policy).

  1. Detection engine computes growth and estimated headroom.
  2. Agent verifies current FRA limit/reclaimability and recent archiver errors.
  3. RAG retrieves approved FRA runbook for applicable Oracle version.
  4. DBA receives evidence, urgency, forecast assumptions and safe investigations.

Potential message: “DB01 FRA is 89%, up 15 percentage points in six hours. Review archive/backup progress and reclaimability. No changes made.”

Reactive

ORA-00257 / archiving-related incident

Trigger: ORA-00257 event captured or matching alert-log evidence.

  1. Open/high-priority incident and notify on-call via rule path.
  2. Correlate disk and FRA usage, instance status and recent backup evidence.
  3. RAG retrieves official and internal corrective procedures.
  4. Agent reports likely root-cause candidates and DBA-approved next steps.

Potential message: “Archiver error detected. FRA pressure is a candidate cause; check logged messages and destination usage. Incident INC-1042 opened.”

10. Security, licensing and operational guardrails

Database security

  • Dedicated least-privilege database service account.
  • Grant narrowly scoped access to required dynamic/DBA views; privilege mapping approved by DBA.
  • Avoid blanket SELECT ANY DICTIONARY or SELECT_CATALOG_ROLE by default.
  • Restrict listener/network access; use TLS and secret storage.
  • Enforce timeouts, query templates, sample rates, and connection budgets.

Agent and application security

  • Per-target role authorization and user identity propagation.
  • Tool-call policy: read-only, allowlisted, audited; no privilege escalation.
  • Block prompt injection from event logs, documents and chat inputs.
  • Protect passwords, SQL text, PII and confidential log fields.
  • Human approval and separate executor for any future remediation.

11. Phased implementation approach

Phase 0

Discovery and safety baseline

Inventory Oracle versions/editions, CDB/PDB shape, Windows releases, target count, log locations, firewall routes, existing observability, licensed packs, on-call workflow and document ownership. Define least-privilege grants, retention and test environments.

Exit criterion Approved data contracts, architecture, target matrix and threat model.
Phase 1

Reliable deterministic monitoring MVP

Build Oracle SQL collectors, event-log ingestion, host metrics, normalized event schema, time-series persistence, thresholds, incident states and email notifications. Test collector outage, duplicate events, clock drift and alert retries.

Exit criterion Reproducible ORA and capacity scenarios produce correctly routed alerts without any LLM dependency.
Phase 2

RAG and DBA chat

Ingest approved Oracle PDFs and DOCX runbooks, build hybrid retrieval + citations, introduce SSO chat and authorized diagnostic tools, and evaluate grounded responses against curated DBA questions.

Exit criterion Operators receive source-linked answers with current telemetry timestamps, and inappropriate tools are denied.
Phase 3

Agentic triage and explanation

Add LangGraph coordinator, specialized triage agents, structured evidence bundles, incident enrichment and bounded multi-step reasoning. Replay historical incidents and compare with DBA assessments.

Exit criterion Higher diagnostic utility without delaying critical notifications or triggering unauthorized action.
Phase 4

Trend prediction and fleet-scale hardening

Introduce baseline-aware anomaly detection, capacity forecasting, maintenance-window suppressions, user feedback, high availability, cost guardrails and enterprise ITSM. Only then evaluate approved remediation workflows.

Exit criterion Validated false-positive rate, alert latency, uptime, audit completeness and fleet load impact.
Suggested POC: Start with two Oracle databases on Windows Server, three incidents (FRA pressure, ORA error, Windows disk/service failure), 20–50 approved support documents and 30–50 golden-set DBA questions. These are planning assumptions, not mandatory product limits.

14. Example DBA questions and safe SQL patterns

Chat scenarios

“How healthy is PRODDB01 right now?”

Orchestrator uses the last successful heartbeat, instance state, FRA/tablespace trend, recent critical alert events, Windows service/disk health and monitoring freshness. It returns a status with observed timestamps, uncertainties and relevant incidents. It does not assume that “no alert” means healthy if telemetry is stale.

“Why did ORA-00257 occur overnight?”

Fetch the alert-log timeline, FRA history, archive destination signals and backup/job receipts using approved tools. Retrieve applicable Oracle documentation and internal SOP. Present ranked causes and the evidence needed to confirm each one, with no automatic archive deletion.

“Which databases may run out of disk in seven days?”

Query historical per-volume and Oracle capacity metrics. Fit a simple trend with seasonality bounds if sufficient history exists; rank risk and disclose assumptions. Avoid extrapolating if retention is insufficient or recent behavior is discontinuous.

“What changed before the performance slowdown?”

Correlate Windows event and resource timelines with accessible Oracle performance counters and change/incident records, while showing when data comes from optional licensed sources. Do not claim a verified root cause based solely on temporal correlation.

Illustrative allowlisted SQL templates

These are starting-point examples for a DBA to review, test and grant at a narrowly scoped level. They are not a complete monitoring pack and may vary with Oracle version, PDB scope, privileges and licensing.

-- Example 1: fast recovery area (FRA) occupancy
SELECT name, space_limit, space_used, space_reclaimable,
       ROUND(100 * space_used / NULLIF(space_limit, 0), 2) AS used_pct
FROM   v$recovery_file_dest;

-- Example 2: instance identification / state
SELECT instance_name, host_name, status, startup_time
FROM   v$instance;

-- Example 3: selected resource headroom
SELECT resource_name, current_utilization, max_utilization,
       limit_value
FROM   v$resource_limit
WHERE  resource_name IN ('processes','sessions');

-- Example 4: recent ADR alert messages (if supported and granted)
SELECT originating_timestamp, message_text
FROM   v$diag_alert_ext
WHERE  originating_timestamp >= SYSTIMESTAMP - INTERVAL '1' HOUR
ORDER  BY originating_timestamp DESC
FETCH FIRST 100 ROWS ONLY;
Important: V$DIAG_ALERT_EXT can be relatively expensive on large diagnostic repositories. Prefer incremental checkpoints and host-side ADR file tailing where appropriate, and benchmark any polling query. The example with sorting and row limiting is for discussion, not a recommendation to execute frequently without testing.

Terminology and Oracle architecture assumptions

“Global gSystem user” needs clarification in Oracle terminology: a single named service identity used across the fleet is not necessarily an Oracle common user. In a CDB, common accounts normally follow the C## naming convention. The safer default is GSYSTEM as a local account in each monitored PDB (or non-CDB), centrally managed through a secrets vault. Root/CDB-level checks require a separately authorized monitoring account and distinct scopes.

17. Updated agentless logical architecture

No custom application agent installed on Oracle Windows database servers

Architecture shows a central data plane. WEF uses Windows' native forwarding capabilities and needs GPO/WinRM setup; Windows operational telemetry is not readable through Oracle SQL alone. Incident detection remains deterministic if the LLM is unavailable.

Frontend design

Database Fleet Overview

Status badges: Healthy / Warning / Critical / Down / Unknown (stale). Include DB version, server, CDB/PDB, service, role, open mode, last successful poll, active alerts, compliance findings, SLA and trend sparkline.

Integrated Agentic DBA Chat

Chat uses natural language but executes only typed tool contracts. Cite live SQL metrics (with observation timestamp) separately from PDF/Word documentation. RBAC by operator/DBA/admin; chat session linked to a target and tenant.

Suggested TypeScript frontend: React, Vite, TanStack Query, TypeScript API types generated from OpenAPI, ECharts/Recharts for charts, WebSocket/SSE for streaming updates, company SSO via OIDC. Python: FastAPI, Pydantic, python-oracledb, APScheduler or Celery/RQ workers, LangGraph, SQLAlchemy, PostgreSQL, document extractors PyMuPDF + python-docx, OpenTelemetry.

tnsnames.ora is a name/address registry, not a credentials file. The backend reads aliases in its configured TNS directory (config_dir or TNS_ADMIN), maps each alias to inventory metadata, and retrieves credentials through a vault. Startup inventory discovery tests each alias; avoid assuming every alias represents a separate instance or that a listener/service proves the database is healthy.

A PDF/Word file must never grant agent permissions merely because it contains instructions. Support delete/reindex and stale-document quarantine.

Oracle ADR alert log over SQL

SELECT originating_timestamp, record_id, message_type,
       message_level, message_text, host_id, component_id
FROM   v$diag_alert_ext
WHERE  originating_timestamp >= :checkpoint_with_overlap
ORDER  BY originating_timestamp, record_id;

Poll V$DIAG_ALERT_EXT using a bounded time window plus overlap; deduplicate using target, container, timestamp, record_id and a content digest. Persist a durable high-water mark in PostgreSQL. Stage normalized records centrally; raw dump-to-file is optional, not required for the agents. In CDB/PDB configurations the visible scope can differ depending on container and privileges; validate on each Oracle release and connect to the appropriate services. Handle DST, timezone, inaccessible ADR, very large logs, duplicate/reordered events, polling lag and alert-view performance. Limit initial lookback and backfill in controlled batches.

19. Safe tool execution and evolving database policy

Separate monitoring from mutating tools

ToolCapabilityExecution policy
get_db_healthInstance status, last poll, log mode, parametersGSYSTEM SELECT only; permitted in chat and scheduled workflows.
list_tablespacesName, type, allocated/used/free, autoextendGSYSTEM SELECT only; permitted in chat.
get_recent_alertsRecent ADR eventsGSYSTEM SELECT only; bounded lookback and rate limits.
propose_users_extension_10gbPlan and preflight a 10GB space additionAnyone authorized to propose; no mutation, includes disk/ASM capacity verification and impact estimate.
execute_approved_users_extension_10gbAdd 10GB OMF datafile to smallfile USERS tablespaceSeparate privileged owner, DBA approval + MFA, target allowlist, change ticket, capacity proof, audit; feature off by default. Bigfile handled differently.

Important: “Extend USERS tablespace by 10GB” is not a generic safe or read-only action. Adding a file, resizing a datafile and changing AUTOEXTEND are different operations. OMF requires a valid file destination; additional free storage and recovery considerations apply. Avoid exposing free-text DDL from an LLM. Use fixed operations + an approval workflow + separately scoped credentials. Underlying ALTER TABLESPACE permissions are broader than this single action; constrain via executor isolation and audited allowlists.

Policy-as-code (example)

policy_version: 1
rules:
  - id: ORA-OMF-001
    title: Oracle Managed Files location is configured
    source: parameter:db_create_file_dest
    check: not_empty
    severity: warning
  - id: ORA-ARCH-001
    title: Database must use ARCHIVELOG
    source: v$database.log_mode
    check: equals:ARCHIVELOG
    severity: critical
  - id: ORA-FRA-001
    title: Fast Recovery Area configured and monitored
    source: v$recovery_file_dest.space_limit
    check: greater_than:0
    severity: warning
  - id: ORA-FLASH-001
    title: Flashback enabled where required
    source: v$database.flashback_on
    check: equals:YES
    severity: warning
    applies_to: [critical_production]

Nuance: DB_CREATE_FILE_DEST being configured is a useful OMF policy signal, not conclusive proof that all existing files are Oracle Managed Files. An FRA can exist without Flashback Database being enabled. ARCHIVELOG, FRA configuration, and Flashback each require separate evaluation. Policy results should be PASS / FAIL / UNKNOWN / NOT_APPLICABLE, with evidence and a policy version, not simply pass/fail.

Change control: policy changes go through version control, test fixtures, peer review, staged deployment and audit. Track exceptions with expiry dates, affected service and owner. Any active policy can vary by prod/dev, Oracle version, architecture and license entitlement.
